Servidor Backend y Modelo de Datos

Infraestructura Backend con Flask

El servidor está implementado en Python utilizando el framework Flask, organizando la API REST mediante blueprints (auth, activities, bot, history, users) protegidos por tokens de acceso JWT y con esquemas de validación de robustez basados en Pydantic.

• Endpoints de Historial: GET /history/ y GET /history/<id>

Arquitectura y Tablas en PostgreSQL (Supabase)

La base de datos relacional está alojada en Supabase y consta de un total de 5 tablas con enumeradores estructurados para la asignación de valores fijos:

• Users: Almacena información relevante de usuarios, incluyendo datos referidos a dificultades de foco registradas (TDA, TDH, TDHA...) para la proposición de planes adecuados.
• Activities: Guarda los datos de las actividades programadas por los usuarios.
• Activity_Types: Maneja la información sobre el tipo aplicado y los tiempos de trabajo y descanso.
• Bots: Contiene la información relativa al robot que pertenece al usuario.
• Histories: Almacena los reportes generados con indicadores precalculados por rangos de fechas.

Desarrollo Hardware y Arquitectura de Firmware

Módulos Electrónicos del Robot

El núcleo electrónico está integrado por el microcontrolador ESP32 (placa NodeMCU) como unidad central de procesamiento acoplado a periféricos específicos:

• Pantalla circular TFT (controlador GC9A01A) comunicada mediante el bus SPI.
• Módulo de audio DFPlayer Mini comunicado mediante bus UART1 con salida a un altavoz.
• Sensor táctil capacitivo TTP223 para el reconocimiento físico de gestos.

Protecciones de Hardware Implementadas

Inserción de una resistencia de 1 kΩ en la línea RX entre el DFPlayer Mini y el ESP32 para eliminar ruidos por picos de tensión residual en la comunicación serie. Uso de un transistor BJT BC547 actuando como mecanismo Low-Side Switch para conmutar el pin BLK de la pantalla y apagar físicamente la retroiluminación en modo SLEEP.

Máquina de Estados Finitos (FSM)

El firmware en C++ implementa una FSM con nueve estados para controlar el comportamiento autónomo del robot (gestión de temporizadores, ciclos y cambios de expresión visual sin depender de comunicación continua):

• IDLE: Estado de espera con parpadeo de ojos fijos (3500ms abiertos, 150ms cerrados).
• RQST: Procesamiento y recepción del comando enviado desde el servidor.
• SLEEP: Pantalla completamente apagada por hardware para ahorro de energía.

Capa de Red y Protocolos de Comunicación

Punto de Acceso y Portal Cautivo

Al arrancar, si el dispositivo no se conecta, entra en modo Access Point (estado AP) desplegando un Portal Cautivo. Este ofrece una página web interna que escanea e identifica las redes WiFi disponibles (banda de 2.4 GHz) para introducir las credenciales de forma autónoma sin alterar el firmware, gestionando hasta tres intentos de conexión.

Sincronización Bidireccional MQTT

Sincronización en tiempo real mediante arquitectura Publish/Subscribe a través de un bróker MQTT central, aislando las vías de comunicación por dispositivo a través de tópicos dedicados basados en identificadores de hardware.

• Tópico de publicación de estado del bot: focusapp/{mac}/status

Flujo de Ejecución de una Actividad

El backend actúa como puente e inyecta los comandos MQTT hacia el robot. Una vez recibida la instrucción, el dispositivo asume la ejecución completa de la sesión. Al finalizar el ciclo o interactuar de manera táctil con el sensor, calcula los resultados y publica la actualización de estado, la cual es capturada por el servidor Flask para persistir de manera íntegra la traza en PostgreSQL y permitir la posterior consulta de históricos.
